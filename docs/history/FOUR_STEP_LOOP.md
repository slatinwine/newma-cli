# 四步循环系统 (Four-Step Loop System)

## 🎯 概述

Newma (牛码) 现在使用**四步循环系统**来实现自主任务完成：

```
推理 → 执行 → 观测 → 修复 → 推理...
```

这个循环系统类似于科学方法（假设→实验→观测→修正），能够自动迭代直到任务完成。

## 🔄 四步详解

### 步骤 1: 推理 (Reason)

**职责**：分析需求，生成推理过程和行动计划

**输入**：
- 用户需求
- 项目信息
- 之前的推理（用于迭代改进）

**输出**：
- 推理过程（思考步骤）
- 置信度 (0-1)
- 行动计划
- 预期结果
- 潜在风险

**文件**: `src/loop/reasoner.ts`

**示例**：
```typescript
🧠 步骤 1: 推理

📝 推理过程：
──────────────────────────────────────────────────
1. 需求分析：用户想要创建登录功能
2. 技术方案：使用 JWT + bcrypt
3. 实施步骤：先创建模型，再创建路由
4. 风险评估：需要处理密码加密
──────────────────────────────────────────────────

✓ 置信度：85%

🎯 预期结果：
  完成用户认证系统

⚠️  潜在风险：
  1. 密码存储安全
  2. JWT 密钥管理
```

---

### 步骤 2: 执行 (Execute)

**职责**：执行行动计划中的操作

**输入**：
- 要执行的操作列表

**输出**：
- 执行状态（成功/失败）
- 已执行的操作
- 输出内容
- 错误信息
- 执行耗时

**文件**: `src/loop/coordinator.ts` 的 `executeStep` 方法

**示例**：
```typescript
⚙️  步骤 2: 执行

执行 3 个操作...

  ✅ 创建 src/auth/login.ts
  ✅ 创建 src/auth/register.ts
  ✅ 修改 src/server.ts

✓ 完成 3 个操作，耗时 1.23s
```

---

### 步骤 3: 观测 (Observe)

**职责**：分析执行结果，判断是否满足需求

**输入**：
- 原始需求
- 当前项目状态
- 执行结果
- 预期结果

**输出**：
- 是否满足需求
- 观测发现
- 发现的问题
- 与预期的差距
- 置信度
- 建议（continue/repair/replan/complete）

**文件**: `src/loop/observer.ts`

**示例**：
```typescript
👀 步骤 3: 观测

分析执行结果，判断是否满足需求...

✅ 状态：需求已满足

📋 观测发现：
  1. 创建了登录和注册路由
  2. 集成到服务器
  3. 代码编译成功

⚠️  发现问题 (0)：

📊 置信度：90%

💡 建议：COMPLETE
```

---

### 步骤 4: 修复 (Repair)

**职责**：基于观测结果，生成修复方案

**输入**：
- 原始需求
- 当前项目状态
- 发现的问题
- 与预期的差距

**输出**：
- 是否需要修复
- 修复方案
- 修复理由
- 预期效果
- 是否需要重新规划

**文件**: `src/loop/repairer.ts`

**示例**：
```typescript
🔧 步骤 4: 修复

基于观测结果，生成修复方案...

💭 修复理由：
  发现类型错误需要修复

🔧 修复方案 (1)：
  1. 🔨 [FIX] 修复类型错误
       操作：2 个

🎯 预期效果：
  修复类型错误，代码可以正常编译
```

## 🚀 使用方法

### 启动交互模式

```bash
npx newma-cli -i
```

### 使用四步循环

```bash
/loop <your requirement>
```

**示例**：

```bash
# 创建新功能
/loop 添加用户登录功能

# 修复 Bug
/loop 修复登录时的 JWT 验证错误

# 重构代码
/loop 将认证逻辑提取到独立模块

# 添加测试
/loop 为认证模块添加单元测试
```

## 📊 循环流程

```
开始
  ↓
┌──────────────┐
│  推理 (1)    │ → 分析需求，生成计划
└──────┬───────┘
       ↓
┌──────────────┐
│  执行 (2)    │ → 执行计划
└──────┬───────┘
       ↓
┌──────────────┐
│  观测 (3)    │ → 分析结果
└──────┬───────┘
       ↓
   是否满足？
   ↙       ↘
 是          否
 ↓            ↓
完成      ┌──────────────┐
          │  修复 (4)    │ → 生成修复方案
          └──────┬───────┘
                 ↓
          是否需要重新规划？
          ↙              ↘
       是                  否
       ↓                   ↓
    回到推理(1)        回到执行(2)
```

## 🆚 对比：新 vs 旧

### 旧的 Plan 模式

```
用户需求 → 规划 → 执行 → 验证 → 完成
```

- 单次规划
- 静态执行
- 简单验证

### 新的 Loop 模式

```
用户需求 → 推理 → 执行 → 观测 → 修复 → 推理 → ...
              ↑_______________________________|
                      循环直到完成
```

- 多次推理和改进
- 动态调整
- 智能修复
- **更自主**

## 💡 设计理念

### 1. 自主性
- Newma (牛码) 自动推理、执行、观测、修复
- 最小化用户干预
- 智能判断何时完成

### 2. 迭代改进
- 每次循环都基于前一次的结果
- 失败的推理会被改进
- 错误会被自动修复

### 3. 可观测性
- 清晰显示每一步的结果
- 完整的推理过程
- 详细的观测发现

### 4. 容错性
- 失败后自动重新规划
- 多次修复机会
- 降级模式（AI 调用失败时）

## 🎨 最佳实践

### 1. 明确的需求

✅ **好的需求**：
```bash
/loop 添加用户登录功能，使用 JWT 和 bcrypt
```

❌ **不好的需求**：
```bash
/loop 修复代码
```

### 2. 合理的迭代次数

- 简单任务：1-2 次迭代
- 中等任务：3-5 次迭代
- 复杂任务：5-10 次迭代

### 3. 监控循环进度

观察每次迭代的：
- 推理置信度
- 执行成功率
- 观测发现的问题
- 修复效果

## 🐛 故障排除

### 循环不终止

**原因**：持续发现新问题

**解决**：
1. 检查观测结果是否合理
2. 调整需求描述
3. 限制最大迭代次数

### 推理质量差

**原因**：需求不明确或项目信息不足

**解决**：
1. 提供更详细的需求描述
2. 确保 README 和文档完整
3. 使用 `/chat` 先讨论方案

### 修复失败

**原因**：问题过于复杂

**解决**：
1. 系统会自动建议重新规划
2. 手动介入，分解任务
3. 使用传统的 `/plan` 模式
